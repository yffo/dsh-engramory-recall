# dsh-engramory-recall

给 [Engramory](https://github.com/tinqiao-oss/engramory) 格式的 markdown 记忆库加四件事：

1. **本地自动召回**：模型不用自觉去读索引，相关的既有笔记会自己浮现到这一轮里；
2. **写入治理**：fail-closed 校验闸门、落盘审计、静态体检；
3. **自动归档**：把追加式的「第 N 批」章节整段搬进 `<笔记>-history.md`，主文件只留结论与现状；
4. **可观测性**：GUI 里一个「记忆」标签页，看得到库里有什么、这轮召回了什么、写得干不干净。

全部用 `node:` 内置模块实现：零第三方依赖、零网络、**默认零模型调用**、零常驻进程
（只有你显式开启可选的语义增强时，才会走宿主的模型服务）。

## 底线

| 底线 | 本插件如何守 |
|---|---|
| 数据不出本机 | 纯 `node:` 内置模块；`capabilities` 只需要 `fs-read` / `fs-write`，不需要 network |
| 不每轮塞正文 | 只在**命中**时注入，且只注入「文件名 + 一行片段」；没命中一个 token 都不注入 |
| 纯文本、可跨 Agent | 只读记忆库的 markdown，不建库、不产生索引文件 |
| 有上限 | 注入量硬上限 `maxChars`（默认 480 字符）+ `maxPointers`（默认 4 条）+ 预算降级阶梯 |
| 不静默改数据 | 召回只读、体检只报告、归档每次都要显式确认且先备份、写入闸门只拒绝不代写 |

## 一分钟选型：先看会不会被卡住

选型的顺序是先排除，再比功能。下面四条否决线是两次真实卸载换来的（云端 Memmy 装上又卸了两遍）。

| 否决线 | 判据 | 倒在这条线上的 |
|---|---|---|
| **数据不出本机** | 正文、embedding、摘要，一个字节都不该离开这台机器 | Memmy（`api.memmy.cn`）、Hindsight（默认上云）、DSH-SEP（抽取走 `api.deepseek.com`） |
| **用不上就不计费** | 没命中就该是零 token、零检索，而不是"少花一点" | Memmy（每轮无条件 550–1550 tokens）、DSH-SEP（每步 ~1250 字符 guidance + ≤4200 字符快照）、OpenViking（强制服务端 + 每轮注入） |
| **不做不可逆的事** | 可以不写，不能替人删 | 所有"自动遗忘 / 自动合并"型方案：删掉的记忆找不回来，而记忆系统的价值恰恰在长尾 |
| **三年后还能跑** | 不需要编译原生模块、不需要常驻服务 | 带 `better-sqlite3` 编译、rust 工具链、独立 daemon 的方案，会在某次系统升级后让你回来看这篇 README |

四问都过了，才轮到比功能。功能这一层，本插件的取舍是**把不确定性变成可测量的东西**：
新机制必须在库上跑出数字，跑不出来就不上（文末五条被证伪的路就是这么留下的）。

### 有几件事不是本插件独有的

写清楚这些，省得读者以为独家：**零模型调用**至少有四家同类做了（`thoth-mem`、
`@max-null/dsh-memory`、`@tr1v3r/dsh-ltm`、`@jipika/dsh-memory`）；
**中文词法检索**也不是独家（`@max-null/dsh-memory` 做 CJK 单字加 2-gram，
`@tr1v3r/dsh-ltm` 做 CJK 二元加 FTS5 混合重排）；**markdown 当真相源**有 basic-memory（AGPL-3.0）；
**写入安全**有 `@jipika/dsh-memory`（写前 guard hook）和 `@tr1v3r/dsh-ltm`（串行写入 + 备份 + 回滚）。

### 确实少见的三件

1. **索引上限做成「拒绝写入」而不是「注入预算」**。同类的超限处理都是软的：
   `@jipika/dsh-memory` 的 `indexBudget` 默认 12000 字符，超了自动回退成索引模式；
   `@max-null/dsh-memory` 逐条截断注入；`thoth-mem` 用 strict character budget。
   本插件的 `index-guard.js` 是在**写入那一刻**拒绝让 `MEMORY.md` 超过 200 行 / 25KB，
   理由是索引每次会话都要整篇读，超限的部分会被静默地不再召回，软处理救不了这件事。
2. **可逆归档**。追加式章节整段搬家、不截断、搬前备份、两段式确认；同类里没有等价物。
3. **MIT + 零依赖 + 零进程**。最强的同生态对手 basic-memory 是 AGPL-3.0 + Python 进程 +
   FastEmbed 权重下载，装它要接受另一套运行时。

### 短板

- **没有公开基准**：`thoth-mem` 公布了 LongMemEval-S 470 题的成绩（RecallAny@5 432/470、
  Recall@5 84.8%、NDCG@10 0.8165、p95 9.35ms）。本插件的探针跑在自己的库上，口径与它不可比。
  下面那一节是自建的可复算基准，但它仍然是自建口径，别当成跨插件排名。
- **无语义检索**：没有 embedding、没有向量库。同义改写、隐含意图要靠手工同义表覆盖，
  没覆盖到的就是漏检。（可选的 `ctx.llm` 模块能做矛盾检测和摘要，但它**不参与检索排序**，
  所以排序本身仍然是纯词面的。）
- **只支持 DSH 一个宿主**：`claude-mem` 覆盖 7 个宿主，`thoth-mem` 覆盖 4 个。
- **没有多端或团队同步**：basic-memory 有云同步，本插件没有。
- **写入闸门可以被绕过**：`guard` 只拦 `write` / `edit` 工具调用，`bash` 重定向它看不见；
  `@jipika/dsh-memory` 的 guard 挂在更底层的 `tools/pre-execute`，覆盖更广。

## 召回质量：两把可复算的尺子

### 一、合成基准（`node bench/run.mjs`）

224 篇程序生成的笔记（中文书面 99 / 英文术语 85 / 口语体 40，其中 42 篇写了 `aliases`）、
683 条查询、固定随机种子。查询按三种风格分开记分：`verbatim` 抄笔记自己的写法（对照组）、
`colloquial` 只用口语说法（与正文没有字面重叠）、`keyword` 口语症状加域特征词
（同域候选很多，必须靠事件词分辨）。语料是程序生成的，不依赖任何私人库，任何人可复算。

| 引擎 | 总 hit@1 | 总 hit@4 | verbatim | colloquial | keyword |
|---|---|---|---|---|---|
| **本插件** | **49.5%** | 57.0% | 100% | 24.1% | 21.9% |
| 教科书 BM25（同分词口径） | 47.0% | 52.0% | 100% | 17.9% | 25.4% |
| 教科书 BM25（中文逐字切分） | 48.6% | 54.8% | 100% | 21.4% | 26.8% |
| 瞎猜（地板线） | 0.1% | 2.5% | 0% | 0% | 0.4% |

（分风格单元格是 hit@1。地板线是实测的随机命中率：`keyword` 的同域候选有 14 篇，瞎猜大约 7%。）

消融，同一份语料，每次只动一个机制：

| 改动 | 总 hit@1 | 相对本插件 |
|---|---|---|
| 本插件 | 49.5% | — |
| 去掉同义表 | 47.6% | -1.9pt |
| 去掉笔记别名（不再声明 `aliases`） | 49.0% | -0.4pt |
| 去掉字段加权（`TITLE_EXTRA` 24 → 0） | 53.4% | **+4.0pt** |
| 同义键碎片不降权（回到改动前） | 47.7% | -1.8pt |
| 桥权重与同义表一致（都算 0.5） | 50.5% | +1.0pt |

「去掉笔记别名」在总分上只有 -0.4pt，但分风格看是 -3.6pt 口语（24.1% → 20.5%）：
别名是作者自己把口语说法钉在笔记上，只对「换一种说法问同一篇」有效，
在语料整体里被别的风格摊薄了。写别名的 42 篇 hit@1 54.8%，没写的 182 篇 17.0%。

最后两行是一次明确的取舍。改动前，桥组（查询里的词在目标笔记里一个字都没有）
只有 27.3%：查询自己的字面碎片（`崩了` 的「了」在别的笔记里到处都是）按满权重计分，
把桥到的词压了下去。修法有两种，一种是把命中的同义键自身的字面碎片从词项里剔掉，
实测**打红了真实存在的测试**：`test/recall.test.mjs` 的注入预算阶梯用 `代理节点与部署` 当查询，
而 `代理`、`部署` 既是同义键、也是笔记正文里的原词，剔掉等于把真证据扔了。
所以改成**降权不剔除**（`BRIDGED_FRAGMENT_WEIGHT = 0.5`，桥到的技术词算 `BRIDGE_WEIGHT = 1`）。

代价是总分少 1 个点（50.5% → 49.5%）。接受它的理由：合成语料里绝大多数查询本来就有字面落点，
总分被它们主导；桥是唯一在字面完全无交集时还能工作的机制，它从 27.3% 到 100%，
而总分只让出 1 个点。消融表里还留着更省事的选项（桥权重打回 0.5），但那条路的桥组只有 90.9%。

「去掉字段加权」那一行要单独说：合成语料里去掉它反而涨 4.0 个点，
而**真实库的中立对照说相反**（见下）。两个结论冲突的原因定位到了机制上：
合成语料的标题是从正文模板派生的、与正文近乎重复，抬高标题权重只是放大域词噪声；
真实库的标题是人手提炼的。所以保持 `TITLE_EXTRA = 24`，冲突如实留在这里，
而不是只挑对自己有利的那把尺子。

### 桥组：11 条，100%

| 组 | 条数 | hit@1 | 说明 |
|---|---|---|---|
| 桥组（全部） | 11 | 100% | 查询与目标笔记的字面重叠为 0，命中只能靠同义桥 |
| 其中公开词族 | 8 | 100% | 调表时看得见的词族 |
| 其中留出词族 | 3 | 100% | 没参与调表的词族，看一点泛化 |

这组查询是从引擎自己读的那张同义表里长出来的，所以它证明的是**扩展管道通不通**，
不是「表能不能猜中没见过的说法」，后者只有留出那 3 条能说一点。
真正的瓶颈在供给面：同义表覆盖了 16 个域词里的 5 个、14 个事件词里的 5 个，
另有一批口语键因为自带字面碎片而够不上「纯桥」资格被丢弃。
224 条口语查询里，字面重叠为 0 的其实只有 28 条 —— 也就是说这批「口语查询」
绝大多数仍能靠碎片碰到笔记，真正需要跨说法的只有那几条。

未命中的查询里，53 条的 top-1 是同一领域里搞错了事件，292 条是同一事件里搞错了领域，
「完全不沾边」和「一条都没召回」都是 0 次。也就是说失败都是「差一点」，
没有灾难性的空召回。

### 二、真库探针（`npm run probe`）

跑在自己的记忆库上，分三组 query 各测一层机制。数字随库变化，每次跑都打印语料指纹，
指纹变了会直接警告「分数不可直接比较」。

| 组 | 条数 | 测什么 | 最近一次 |
|---|---|---|---|
| 口径 | 21 | 真实场景的中文口语问法 | recall@4 21/21 |
| 桥探针 | 10 | 全局同义表（大白话问英文/术语密集的笔记） | recall@4 9/10 |
| 别名探针 | 5 | 笔记自己的 `aliases:`（关键词在全局桥里一个都没有） | recall@4 5/5 |
| 死桥自检 | 301 值 | 同义桥的每个值是否真的存在于语料（不存在等于白写） | 25 个死值（均为通用词） |
| 对照 A | 175 | 文件名当查询的底线（对标题权重有偏袒） | top1 41/175 · recall@4 94/175 |
| 对照 B | 150 | 笔记中文标题当查询的底线（同样偏袒） | top1 145/150 · recall@4 149/150 |
| 对照 C | 162 | 正文独有词当查询（该词在任何标题里都没有） | top1 126/162 · recall@4 149/162 |

对照 A 和 B 都拿标题当查询，所以它们对「标题里的词多计几遍」这类参数是**结构性偏袒**的：
抬高标题权重几乎必然让这两组变好。它们既不该当目标函数，也不能用来证明「抬高标题权重是安全的」。
唯一中立的是对照 C：查询词取自某篇正文、且任何标题里都没有它，此时抬高标题权重
只会让标题里恰好撞上这个词的别的笔记平白加分、把正确答案挤下去。`TITLE_EXTRA` 的值就是按 C 定的。

探针存在的理由值得单说：`bm25.js` 里的同义表与 `EXTRA_WEIGHT` 是语料统计量撑起来的经验值，
在小 fixture 里测不出差异。写过一版单测，权重从 0.5 改到 0.8 两边都绿，
因为小库里 df 结构整个反过来。那种测试给的是假安心，已删掉，证据改由探针在真实库上产出。

它也确实拦下过一次误判：`EXTRA_WEIGHT` 一度被提到 0.8（当时量到口语 query 19/22 → 20/22），
但那是同义表还没补全时量的。等最后几条桥补完再重量，0.5 和 0.8 的三项数字一模一样
（口径 19/21、对照 A 22/82、对照 B 136/142），说明那 1 分来自补桥、不是来自权重。0.8 因此退回 0.5。
**A/B 要在最终状态上做，中途的差值可能只是「另一半还没做完」。**

还有一个坑：探针跑的是真实记忆库，库一变分数就会动。撞过一次，某篇笔记里逐字抄了探针的 query，
自己成了第一名，把真正的目标挤下去。现在写调优笔记一律不引用探针原文。

这个坑现在有机器化的答案：每次跑探针都打印一枚语料指纹（`store.js` 的 `corpusFingerprint`，
把每个 chunk 的 `id / title / description / aliases / body` 哈希成 12 位十六进制），并和基线比对：

- **指纹相同、数字有变**：这是一次可信的 A/B（改了代码，卷子没换）。
- **指纹不同**：直接警告分数不可直接比较。

指纹的第一版只哈希了 `id + body`，于是只改 `aliases` 时它纹丝不动，而 `aliases` 是被计两遍、
实打实改变排序的。结果探针一边说「语料没变、这是可信 A/B」，一边把一次语料改动伪装成了代码改动。
**一个漏字段的指纹比没有指纹更坏**，因为它是权威口吻的错误。现在指纹覆盖所有喂进索引的字段，
并有专门的回归测试守着。

## 工作机制

### 召回：发生在每个用户轮的第一个 step

1. 取这批消息里最后一条**真人**消息，做可检索性门控：空、寒暄（继续 / 嗯 / 好的 / ok…）、
   短于 4 字的消息直接放行，零开销；
2. 超长消息头尾各取一半（中间通常是粘贴的日志或正文，噪音最多），头部再收敛到前 3 句；
3. BM25 检索 + 同义扩展 + IDF 选词，取前 `maxPointers` 条；
4. 命中就追加一条 `role: user` 的插件消息（`source.kind = plugin:dsh-engramory-recall`、
   `form: notice`），内容是「可能相关的既有条目」：文件名 + 命中行片段 + 一句「需要细节自己 read」；
5. 没命中就原样放行。

### 十个机制

| # | 机制 | 治什么 |
|---|---|---|
| 1 | 同义扩展（105 条口语→技术词）+ 连字符再切分 | 中文口语与笔记用词对不上的同义鸿沟 |
| 2 | 超长正文按 `##` 切桶 + **整篇**长度归一 | 单篇巨文霸榜（一篇几百 KB 的笔记曾占掉四分之一召回位） |
| 3 | 寒暄 / 极短消息门控 | 「继续 / 嗯」这类消息 10/10 注入噪音 |
| 4 | 写入闸门（fail-closed） | 不合规文件名、缺失 frontmatter、疑似真实凭据 |
| 5 | 注入去重 | 同一批指针上一轮已在上下文里，不重复计费 |
| 6 | 预算降级阶梯 | 装不下的条目塌缩成只剩文件名，而不是静默丢掉 |
| 7 | 跨轮轮换降权 | 最近注入过的条目在后续轮次乘 0.5，把机会让给别的笔记 |
| 8 | 沉淀提醒 | 长会话一次都没写过记忆库时，提醒一次，补「该记的没记」 |
| 9 | 索引上限闸门（`index-guard.js`） | `MEMORY.md` 长过 200 行 / 25KB 就拒绝写入，索引是每次都读的，超限部分会被静默地不再召回 |
| 10 | `engramory` 技能（`skill.js`） | 「什么时候该记、什么时候不该记」这套纪律本身，注册成技能才不依赖外部插件 |

9 与 10 是从另一个只做这两件事的插件整个融进来的（逻辑与措辞逐字保留），
融进来之后它就可以从 profile 里摘掉。理由不只是省一个依赖：两套闸门各管一半
（这边管笔记文件、那边管索引），判据一旦漂移就会互相打架，而这个项目已经因为
「同一个概念有两处定义」栽过三次（见文末）。一个概念一处定义。

### 写入闸门（`guard.js`）

注册为宿主的 `ctx.tools.guard()` 单调守卫：模型用 `write` / `edit` 往记忆库里写时先静态复核，
不合规就拒绝这次工具调用（拒绝理由直接回给模型），且后续监听器无法把拒绝翻回允许。

| 判定 | 规则 |
|---|---|
| 文件名 | 必须匹配 `<user\|feedback\|project\|reference>-<小写slug>.md` |
| frontmatter | 必须有头部块，且含 `name` / `description`，`type` 与文件名前缀一致 |
| 凭据 | 6 类真实密钥（私钥块 / `sk-` / `ghp_` / `AKIA` / `xox` / JWT）+ 键值对形式；占位写法放行（`process.env.X`、`<YOUR_TOKEN>`、`CHANGEME`、`***`…） |
| 体积 | 单篇 ≤ 100KB |

`edit` 只能看到片段、看不见结构，所以它只查文件名与凭据（返回 `partial: true`）。
放行与拒绝都追加到 `<storePath>/.engramory-audit.jsonl`（JSONL，含 `epoch` 规则版本，
超 512KB 自动轮转）。

**边界**：`guard` 只拦 `write` / `edit` 工具调用，`bash` 重定向它看不见。它是正路守卫，
不是沙箱；兜底靠体检器定时扫（真实抓到过两篇绕过闸门的裸 markdown）。

#### 不用信这段话，两分钟自己验一遍

闸门跑在宿主进程里，验法就是在你的 agent 会话里让它做下面四件事 —— 全部走普通的 `write` / `edit` 工具，不需要装任何东西：

| 让它做 | 你会看到 |
|---|---|
| 往 `MEMORY.md` 追加 130 行（凑到 203 行） | 拒绝：**「这次写入会把索引 MEMORY.md 顶过上限（203 行 > 200）」** |
| 在记忆库外（比如项目目录里）写一份同名、同样 203 行的 `MEMORY.md` | 放行（闸门只认配置的那一个库） |
| 往库里写 `bad-name.md` | 拒绝：**「文件名不合规。必须是 \<user\|feedback\|project\|reference\>-\<小写slug\>.md」** |
| 写一篇带 `api_key: sk-…` 的笔记 | 拒绝：**「疑似含真实凭据（OpenAI 风格密钥）」** |

作者实测（0.5.1 / 2026-10-15 / 库 63 篇、索引 73 行）：四条全中，两次被拒的写入**磁盘上零字节变化** —— 被拒后索引与操作前逐字一致。

这就是它跟别家最本质的一处不同：别人的记忆预算卡在**注入**上（超了就少喂几段给模型），这里卡在**写入**上 —— 索引文件本身长不到超限，所以「超限的部分静默不再被召回」在这个库里不会发生。

### 体检器（`doctor.js`）

纯静态、只报告不动手。12 项检查：库不可读、索引指向不存在的文件、孤儿笔记、索引重复、
文件名不合规、`name` / `type` 与文件名不一致、缺 `description`、超 100KB、待办 30 天没更新、
失联路径（同一目录名出现在多个位置、其中有的已不存在）、归档建议（超 64KB 或追加章节超过 20 个）、
疑似重复主题。

三条防误报纪律：路径比较前先规范化（`~/x` 与 `/Users/you/x` 同处、尾斜杠不算另一个位置、
含 `...` 的是缩写、一层深的隐藏目录如 `~/.dsh` 是各工具自己的配置位不算冲突）；
缺 `description` 时不参与相似度比较（否则 `undefined` 会变成共同 token 算出假相似）；
判断路径是否还在要用 `statSync` 不抛错，不能用 `isFile()`（软链指向目录时它返回 false）。

它不做纯词面的语义冲突检测，这条路已实测证伪：对全库笔记两两算词面相似度，
最高的一组（0.445）全是毫不相干的项目，它们像只是因为共用同一套文档模板措辞。
纯词面测的是文体不是主题。要测语义冲突只能过模型，见下面的可选项。

### 沉淀提醒（机制 8）

补的是唯一一个不受任何约束限制的缺口：闸门保证写进来的东西干净，
但没有任何机制保证该写的被写了。判据刻意保守，三条同时满足才提醒：

- 本会话轮次 ≥ `sedimentMinTurns`（默认 12）；
- 本会话对记忆库的成功写入次数为 0；
- 距上次提醒 ≥ 24 轮。

短会话不触发，已经在写的会话永远不触发。它独立于召回命中（命中为 0 时才更需要它），
也不参与注入去重（去重讲的是上一轮那份指针还在，它讲的是本会话一直没写过）。

### 归档（`archive.js`）：把历史搬走，不把历史删掉

追加式写法（每批上线往同一篇笔记后面接一段）会让一篇笔记长到几百 KB。检索时它按整篇长度归一，
于是长期霸占召回位。归档做的是物理分层：

- **只搬追加式章节**：认 `## 第 N 批` / `**第 N 批**` / `### 第 N 批`（中文数字也认）。
  正文里的结论、现状、非批次章节一律不动。
- **搬进同目录的 `<笔记>-history.md`**：仍在库里、仍被 `readDocs` 索引、仍能被召回，
  所以没有一步是不可逆的。超过 90KB 自动续写到 `-history-2.md`，因为写入闸门对单篇
  有 100KB 上限（第一版没做分组，一份 151KB 的历史被自己的闸门拒了）。
- **先备份再动手**：原件写入 `.archive-backup/<时间戳>/`（只读快照，`readDocs` 不递归，不进检索）。
- **两段式**：`planArchive` 只读预览，面板点「执行」才动库，且每次执行前重新出具计划。
- **可以再来一层**：搬出来的 history 笔记本身也可能长回去。归档器认得出自己的产物，
  `baseSlug()` 把 `x.md`、`x-history.md`、`x-history-2.md` 归成同一篇，于是
  `history-2.md` 能再拆出 `history-5/6.md`，新文件名从不撞已有的。
  它也不会去归档自己的归档：文件名过滤 + 计划时按已有的批次标题去重，两层都在。
- **不碰 `MEMORY.md`**：索引由另一套守卫管，归档是机械派生、不产生新事实。

示例效果（示例库，数字只说明数量级）：单篇 260KB 压到 8KB，46 个批次搬进 4 份 history 笔记
（37 / 90 / 89 / 46KB，都在闸门上限以内）。召回反而变好：原来这篇自己霸榜，
现在命中的是它的 history。

**一次自我纠错**：第一版只认 `## 第 N 批`，而真实那篇里同时存在 `## 第二十七批：…`、
`**第二批：…**`（加粗整行）、`### 第三十八批（…）` 三种写法。判据比数据窄，于是 46 个批次
只看见 32 个，搬完主文件还有 116KB，被闸门**正确地**拒了，而界面上看起来像功能坏了。
现在三种写法都认，且体检器不再自己抄一份正则，而是直接调 `planArchive`。同一个毛病
在这个项目里犯过三次（另外两次是体检器的绝对路径只认 `/Users/`、探针指纹漏算 `aliases` 字段），
所以它现在是一条明确的搜索模式：**判据比数据窄，且失效时不报错**。

### 「记忆」标签页

客户端 bundle 是手写的（`client/client.js`，不需要任何构建工具，只 `require` 平台的
react + primitives），注册到宿主的 `conversation.view` slot，与「对话 / 轨迹」并排。

六个页签：召回日志（每轮判定：注入 / 无命中 / 跳过 / 拦截写入 / 沉淀提醒 / 归档，带展开明细）、
笔记（可过滤的清单）、体检（doctor 的发现，按严重度排序）、索引原文、
归档（待归档计划 + 一键执行）、写入审计（每条放行与拒绝都留痕）。

数据来自插件注册的只读路由 `GET /api/engramory-recall/state`（面板每 3 秒轮询；
体检与归档计划按 30 秒 TTL 缓存，不重算全库）。执行口是另一条必须 `POST` 的路由
（`{ file, confirm: true }`，GET 一律 405）。用 `ctx.inject(['webServer'], …)` 注册：
Electron 载体走 `file://` + IPC 时可能没有 webServer，那时召回照常工作，只是没有面板数据。

### 按需检索工具

`engramory_search({ query, limit? })`：自动召回没命中时的兜底。模型可以主动搜记忆库
（BM25、只读、离线），拿到「文件名 + 命中片段 + 分数」，再自己 `read` 正文。

## 桥与别名：两个调参口

召回准不准，九成取决于「你会怎么问」到「笔记里怎么写」之间那座桥。桥有两层。

**全局同义表**（`bm25.js` 的 `SYNONYMS`，105 条 / 301 个值）管的是一类说法：
`梯子 / 翻墙 / 科学上网` → `proxy, http-connect, socks5`。同义项默认按 0.5 权重计入，
查询命中了某个键时，桥到的技术词按 1 计入、该键自身的字面碎片降到 0.5（上一节的取舍）。

**笔记自己声明的别名**（frontmatter 的 `aliases:`）管的是这一篇：

```yaml
---
name: reference-example-proxy-node
description: 自建代理节点的现状架构：双端口为主 + 兜底链路
type: reference
aliases: 梯子, 翻墙, 科学上网, 节点, 代理
---
```

别名按重复两遍计入，也就是满权重：它是作者点名说的「这篇就管这个词」，
语气比全局桥硬。所以要区分几篇长得很像的笔记用别名，要教会一类说法用同义表。

别名机制早就在仓库里，但在真实库里长期零使用（一份库里 0 篇写 `aliases:`）。
给 8 篇补上之后，别名探针那一组从 1/5 提到 5/5。

### 桥和别名是怎么挖出来的

凭直觉往表里塞词，看着很努力，其实大半是零收益，因为同义词只有在语料里真的存在时才加分。
流程是反过来的：

1. **先量语料**：拉出全库词项与 `df`（出现该词的 chunk 数）。`df` 低的才是专有名词、
   技术栈名，才有区分度；`df` 等于库容量的（如 `kb`）是噪声，拿它做桥等于没有。
2. **再倒推口语**：拿着这些锚点问自己「人会用哪句大白话问它」。
3. **只写语料里存在的锚点**：库里没有 `latency` 这个词，就不写 `节点慢: ['latency', ...]`，
   写了永远是零分，只会让表看起来很长。
4. **每条桥都要有 query 证明它在工作**：探针的桥探针十组就是干这个的。
   某条桥在探针里没有任何一条 query 用到，就删掉。
5. **死值自检**：同义桥的每个值都要在语料里真的存在才有分。指向一个库里根本没有的词，
   效果是写了等于没写：不报错、不降级，最安静的那种失效。探针每次跑都数一遍。

第 5 条当场抓出 32 个值指向不存在的词（`latency`、`slide`、`cert`、`gpt`…），
其中 7 个是同一轮刚加的，也就是说「按语料锚点写桥」这件事当时并没有做到。删掉后剩 25 个，
但那 25 个不该删：它们随插件一起发布，要服务的是任意一份记忆库（别人库里当然可能有
`permission`、`hang`、`gpt`）。**「这条桥有用吗」的答案取决于问的是哪份库**：
自用可以按自己的库裁剪，发布就得留通用词。两者混在一起谈，就会一边留着死重、
一边把别人的桥删掉。

## 它不做什么，以及还做不到什么

### 一、自愿的约束（能做到，但不做）

- **不写记忆库**：写入只由人和模型判断，走 Engramory 的纪律。一个能自己往库里塞东西的
  记忆插件，等于把用户的笔记变成模型的草稿纸。
- **不删任何东西**：没有自动遗忘，没有自动合并。「合并」意味着原文消失。
- **不建第二份存储**：不建 SQLite、不建向量库、不生成索引文件。markdown 是唯一真相源，
  可读、可 diff、可手改、可跨 Agent 共用。

### 二、真的短板（还做不到）

- **不做语义检索**：没有 embedding、没有向量库。中文用「单字 + 相邻双字」切分，
  同义改写、隐含意图会漏检，目前唯一的桥接是一张 105 条的手工同义表。
  需要模型的那两件事（矛盾检测、摘要）做成了可选工具（见「可选：语义增强」），
  但它们不参与检索排序 —— 排序仍然是纯词面的，这一点不打算含糊。
- **没有公开基准**：只有自建口径的合成基准与真库探针（见上），跨插件排名无从谈起。

### 三、曾经没做、现在补上了

- **不自动归档**：已实现。它原来确实写在这一节里，理由也写了「不可逆」。
  但确定性分层不需要 LLM，只是当时没做，所以补上了。
- **同义鸿沟**：同义表已扩到 105 条并逐条经探针验证；笔记别名也真的被用起来了。
- **不自动合并**：降级成只出报告（体检器报疑似重复主题与失联路径），不改文件。

### 路线图

| 缺口 | 计划 | 状态 |
|---|---|---|
| 追加式日志撑爆单篇 | 物理分层归档，零 LLM | 已实现 |
| 同义 / 别名鸿沟 | 同义表扩容 + 别名自动利用，零 LLM | 已实现 |
| 自动合并 | 只出报告，不自动改文件 | 已实现（只报告） |
| 语义冲突检测 | 走宿主 `ctx.llm`，**默认关闭** | 已实现（`semanticConflicts`） |
| 自动摘要 | 走宿主 `ctx.llm`，**默认关闭** | 已实现（`semanticSummary`） |

后两条默认关闭，是为了让「零模型调用」这条基线保持可复现。开启是用户的显式选择，
而不是装完就生效：一个会自己调模型改写你笔记的插件不该默认打开。走 `ctx.llm`
意味着用宿主已经配好的模型，插件自己不配 key、不直接出网。

### 可选：语义增强（`llm.js`）

词面检索对「换一种说法」只能靠同义表，而「两篇笔记互相矛盾」这种判断词面根本测不出来
（实测过：对全库笔记两两算词面相似度，相似度最高的那些对全是不同主题）。这两件事只能过模型，
所以做成了两个**显式开关**，默认关闭：

```yaml
        semanticConflicts: true   # 注册 engramory_conflicts：让宿主模型找出互相矛盾的笔记对
        semanticSummary: true     # 注册 engramory_summarize：把一篇长笔记压成一段话
        llmProvider: ''           # 留空就用宿主的默认模型
        llmModel: ''
        llmTimeoutMs: 30000
```

关着的时候**连工具都不注册**，模型根本看不到这两个入口；开着时也只在工具被调用那一刻
才 `await import('./llm.js')` —— 静态依赖图里没有它，所以自动召回、面板、体检、写入闸门
在任何情况下都不会顺带发一次模型请求。这条承诺是结构上成立的，不是靠自觉。
（`test/llm-wiring.test.mjs` 就是钉这条的：默认只注册一个工具，且 `index.js` 里
不许出现静态 import。）

开启后会多花模型 tokens，用量上限是明说的：一轮冲突检查最多 4 次调用 × 每次 20 篇，
单篇正文超过 1200 字符会截断，**没查到的部分会如实报出来**（`semantic-truncated`），
不假装全看过。模型编造的文件名一律丢弃（只认本批真实文件名），
丢弃的条数也会报出来 —— 宁可显示「这次有 2 处输出不可信」，也不拿它冒充发现。

## 配置

改 profile 的 `cordis.patch.yml`（改完要重启 App 才生效，宿主进程会缓存 ESM 模块）：

```yaml
- insert:
    - id: engramory-recall
      name: dsh-engramory-recall
      config:
        enabled: true            # 总开关
        storePath: ~/memory/engramory
        maxPointers: 4           # 最多注入几条指针
        maxChars: 480            # 注入文本硬上限（字符）
        minScore: 0              # 提高它可以过滤弱命中
        queryChars: 400          # 检索的查询字符预算（超长消息头尾各取一半）
        nudge: true              # 「长期记住」意图提示
        nudgeSediment: true      # 沉淀提醒
        sedimentMinTurns: 12     # 沉淀提醒的轮次门槛
        guardWrites: true        # 写入闸门
        dedupeInjection: true    # 注入去重
        rotationPenalty: 0.5     # 跨轮轮换降权（1 = 关闭）
        rotationHistory: 32      # 轮换记忆长度
        # 下面两个默认关闭：实测无净收益，留着等库里出现半年以上的跨度再复测
        decayHalfLifeDays: 0     # freshness 指数衰减
        recencyWeight: 0         # 时间乘性加权
        autoArchive: false       # 全自动归档（默认关：归档是改库，先手动点几轮再决定）
        indexMaxLines: 200       # 索引 MEMORY.md 的行数上限
        indexMaxBytes: 25600     # 索引的字节上限
        registerSkill: true      # 注册 engramory 技能（写入纪律的正文）
```

`autoArchive` 打开后归档会在两处自动跑：每轮 pre-step 兜底（10 分钟 TTL，不会每轮扫库），
以及写完记忆库的那一刻（触发源记为 `write`）。它仍然先备份、仍然过写入闸门，只是不再等你点按钮。

## 安装 / 卸载

```bash
npm i dsh-engramory-recall                                          # 从 npm 装
dsh plugin --profile <profile> add /path/to/dsh-engramory-recall     # 或从源码目录装
dsh plugin --profile <profile> remove dsh-engramory-recall
```

安装后确认 profile 的 `node_modules/dsh-engramory-recall` 软链指向真实目录。
软链断链时宿主只会打印一行 `skipping profile bundle`，插件整轮不加载却不影响其它功能，
这个坑踩过一次，代价是三天无效测量。

**`dsh plugin` 是全有或全无的**：它每次都会重装 profile 的整个依赖集，所以只要
`package.json` 里有任何一个 spec 解析不了（版本被 registry 下架、被供应链策略拦住、
指向已删的路径），添或删任何插件都会一起失败，而且报错说的是那个无关的包。
排查时看 `.plugin-manager/logs/operation-*/pnpm.log`，别盯被操作的那个包。

## 测试与自检

```bash
npm test        # 分词 / BM25 / 切桶 / 门控 / 闸门 / 索引闸门 / 技能注册 / 体检 / 审计 / 沉淀提醒 / 归档 / 打包 / 路由
npm run check   # 接线自检：配置键认不认、库路径对不对、装的是哪一份、包清单漏没漏文件
npm run probe   # 召回质量探针：3 组 query + 三道对照，跑在真实记忆库上
npm run probe -- --save   # 把这次结果存成基线，之后每次跑自动比对
node bench/run.mjs        # 合成基准（含消融与参数扫描）
```

前三条是克隆仓库开发时用的：`test/`、`scripts/`、`bench/` 不在 npm 包的 `files` 白名单里。
发布出去的是运行时真正需要的那十几个文件（`npm pack --dry-run` 可核），
其中 `package.test.mjs` 会从 `index.js` 递归跟所有 `./x.js` 的 import，逐个核对是否都在白名单里。
这个检查已经抓到过两次真事故（漏 `audit.js`、漏 `archive.js`），两次的后果都是
别人装上一装就 `ERR_MODULE_NOT_FOUND`、整个插件加载失败。

`npm run check` 覆盖的五种**静默失效**（不报错、只是从此不干活）：配置键打错字、
库路径指空、profile 里跑的不是你改的那份、`files` 白名单漏文件、这一行被 `enabled: false` 关掉。
它顺带跑一遍 `node --check` 校验客户端 bundle 的语法（面板写坏了不会连累宿主加载）。
唯一做不了的是活体守卫测试：守卫只拦 `write`/`edit` 工具调用，脚本写盘会绕过去，
所以脚本最后打印的是要由 agent 亲手执行的两个方向探针。

## 集百家之长

四家同类插件的源码逐个读完（hindsight / 灵枢 dsh-memory / dsh-mnemon / dsh-mneme），
产出要求是「机制 + `文件:行号` + 能否在纯 JS、零依赖、零出网下复刻」。能搬的搬，
搬不动或搬了没用的当场证伪。

| 机制 | 抄自 | 结果 |
|---|---|---|
| 注入去重 | dsh-mnemon `src/host/lifecycle.ts:339-345` | 落地，但必须换键：它比的是整段渲染文本，而本插件有跨轮轮换会改变渲染文本，照抄就是死代码（真库探针抓出来的，单测当时还是绿的） |
| 注入预算降级阶梯 | dsh-mneme `src/inject.js:232` | 落地。装不下就塌缩成只剩文件名，不再静默消失 |
| 跨轮轮换降权 | dsh-mneme `src/inject.js:101` | 落地，配套细节不可省：候选池要同步扩容 3 倍，否则降权只是让位子空着 |
| IDF 选词 cap | hindsight `engine/search/bm25_term_selection.py` | 落地，但只能对 `df > 0` 的词排名。按 df 升序取最低的 24 个，留下的全是库里没有的词，实测注入 0 条 |
| fail-closed 闸门 | 灵枢（它只看 `committed` 字段，`ok:true` 不算数） | 落地 |
| 长查询取样 | 灵枢 issue #108（长查询只有开头段进键） | 落地。本插件犯的是反方向：原来只取尾部 400 字符，把开头的主题句整个丢了 |
| 自动归档 | dsh-mneme `src/dream/sleep.js:411` `phaseDemotion` | 落地但换了实现：它截断 + 存 `_full_content`，本插件整段搬家、不截断 |
| 时间衰减 | 灵枢 `rust/src/freshness.rs` | 实测证伪。六档半衰期扫描，recall 恒定、top-1 只有一档 +1（噪声级）。它能用是因为它的 `protected_floor` 依赖人工 `importance` 字段，Engramory 笔记没这个字段 |
| 时间乘性加权 | hindsight `engine/search/reranking.py:35-37` | 实测证伪。五档扫描净收益为零，`w ≥ 0.1` 起还要拿对照组去换 |
| 同义表扩容 | 灵枢的语义归一化 | 落地。105 条桥 / 301 个值，每条都经探针验证，另加一道死桥自检 |
| 查询侧同义词要先分词再算 | 自己踩的坑 | 落地。中文同义词原样返回时永远匹配不上「英文整词 + 汉字双字」的词项形状，写了等于没写且不报错。英文同义词 tokenize 后等于自身，所以这毛病藏了很久 |
| 笔记级别名（`aliases:`） | dsh-mneme 的 `aliases` 钩子 | 落地。机制本来就在（计两遍 = 满权重），但真实库里 0 篇在用；给 8 篇补上后别名探针 1/5 → 5/5 |

**搬机制最容易犯的错**是把机制搬过来、却没搬它依赖的不变量。dsh-mnemon 没有跨轮轮换，
所以它的「渲染文本不变」是真的不变；加上轮换之后，同一个写法就成了永远不触发的死代码。
抄之前先问它凭什么成立、那个前提这里有没有。

## 五条被实测证伪的路

| 尝试 | 结果 |
|---|---|
| 提高分数门槛 / IDF 门槛过滤误召回 | 正例最低分 4.59、反例最高分 5.54，区间重叠切不开；IDF 门槛会把 recall 从 28/28 打到 13/28 |
| freshness 时间衰减（学灵枢 / dsh-mneme） | 六档半衰期扫描：recall 恒为 28/28、top-1 只有一档 +1（噪声级）。库里「旧」的那批恰好是基础事实，衰减就是误伤 |
| 时间乘性加权（学 hindsight） | 五档扫描净收益为零，`w ≥ 0.1` 起反而伤对照组 |
| 给一个已有同义桥继续加词（`主题` 从 `['theme']` 扩到含 `light-dark / color-mix / data-theme / token`） | 看着全是相关的技术词，实测对照 B 掉 3 分（136→133）。机制：把词加进查询扩展后，同一篇笔记自己的其它 chunk 会把「标题里真的写着这个词」的那个 chunk 挤下去，长笔记里这叫自己跟自己抢。判据不是「这词相不相关」，而是「加了它，谁会往上浮」。这 4 个词已全部退回 |
| 拿偏袒的对照当护栏：用对照 A/B 证明「抬高标题权重是安全的」 | 它们都拿标题当查询，对标题权重结构性偏袒，抬高它必然让两组变好。这不是证据，是同义反复。`TITLE_EXTRA` 第一次定成 3 就是被这个漏洞困住的（「口径在 3 之后不再动，所以后面的增量全来自对照」，而对照根本测不出这件事）。补了中立的对照 C 之后，数据说 3 太保守：C 从 0 到 96 一路不降，在 24 到达平台。已按 C 的拐点改成 24 |
